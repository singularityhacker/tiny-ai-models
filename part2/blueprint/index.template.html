01 / Pick the minds

A shortlist that fits on a flash drive.

Recommend the base checkpoints below for a common zero-shot, likelihood-scored study. This aligns with the original base-model evaluation. These are candidates to measure, not a claim that we already know the winners.

__MODEL_CARDS__

Sizes are verified sums of the publisher’s root safetensors weight files at the linked revision, including vision weights where packaged. Tokenizers, configuration, libraries, corpus and runtime caches are extra. Download size ≠ RAM/VRAM. Peak memory is unmeasured. Use one model at a time with a short context; do not allocate the advertised maximum context.

Why base models first?

The existing harness scores the probability of each answer choice. Base checkpoints allow the same plain-text protocol across families. Qwen’s post-trained variants are equally small; an instruction-following / chat study would use those with an explicitly different protocol.

Qwen3.5 uses a newer hybrid architecture. We must validate a pinned current Transformers + lm-eval adapter and text-only likelihoods before launch. The starter’s older environment is not assumed compatible.

The historical correction

The article describes a 1B model at 53.92% MMLU. The recovered result file attributes that score to Llama 3.2 3B. Preserve both facts; do not relabel the old result.

Llama 1B is a new historical-era comparator, not a reproduction of that 3B run. The original 3B weights are 6.43 GB, outside this proposed 5 GB cap. Their scores stay in the archive; a new 3B run needs a separate size exception.

02 / Build the laboratory

One temporary worker. Durable evidence.

Proposed region: us-west-2. An ephemeral EC2 GPU instance runs retrieval and model evaluation in sequential phases. S3 retains the inputs and outputs. Netlify keeps serving the public website after all experiment compute is gone.

Why EC2 for this experiment?

Exact open-weight checkpoints and answer-choice likelihoods matter more than an always-on API. Self-hosted batch inference gives us control of weights, precision, context and scoring. A proposed g5.2xlarge provides a 24 GiB A10G GPU and 32 GiB system memory; fit, quota, capacity and price still require validation.

Retrieval uses a local FAISS + BM25 index, saved to S3 between sessions. No continuously billed search cluster is required for this first panel.

What the AWS work demonstrates

Declarative CloudFormation, temporary compute, IAM instance roles, encrypted S3/EBS, Systems Manager, CloudWatch, budget reconciliation and automated expiry.

SSM access with no inbound SSH or inference port. Outbound HTTPS uses a temporary public address with inbound traffic denied; include its charge. Avoid a NAT gateway for the pilot. A separate local scorer uses a gold-reading role; the worker role cannot read gold.

Why not Bedrock, SageMaker endpoints or Step Functions first?

They remain valid alternatives, but this proposal needs exact small checkpoints and likelihood scoring, with one short-lived worker. Managed generation-only APIs would require a different scoring track. A persistent endpoint, managed vector store or multi-service workflow adds setup and potential idle charges without answering the initial research question. Bedrock reranking can be a later, explicitly costed comparison.

03 / Give them a better library

Three paths. One fair comparison.

Each arm gets the same frozen questions. The two RAG arms share corpus, chunks, embeddings and a maximum of three final chunks / 1,536 corpus-token context. Question stems drive retrieval; options enter only the answering prompt. Gold labels never enter either.

Rewrites computed once

Qwen3.5 0.8B post-trained

The 1.75 GB post-trained sibling generates three short search variants from each stem. Freeze and inspect those variants before scoring. Charge their compute once; share them across all contestants.

Invalid or duplicate rewrites are recorded. No answer choices or gold are supplied.

Single search uses one vector query and the top three chunks. Multi-search uses hybrid vector/BM25 fusion, then cross-encoder reranking. A later ablation can hold the candidate pool fixed to identify which change helped. Retrieval evidence is precomputed for quality; an uncached timing subset measures the full path.

04 / Make the comparison credible

Small panel. Explicit limits.

Freeze

114 MMLU questions: two per each of 57 subjects. 100 HellaSwag validation items. Seed 20261026. Pin task revisions, IDs, hashes, prompts and tokenizer.

Evaluate

214 items × 3 models × 3 arms = 1,926 scored answers. Four candidate likelihoods per item = 7,704 continuation evaluations, not generation API calls.

Explain

Report MMLU accuracy, HellaSwag raw and normalized accuracy, paired improvements and harms, uncertainty, peak memory, stage latency and cost. No blended “overall intelligence” score.

Before the panel: a tiny smoke test

Five MMLU global-facts questions + five HellaSwag questions × three models × three arms = 90 scored answers. Check all adapters, evidence, parser/scorer, cost logging, timeout and teardown within the $20 allocation.

Use disjoint development items. No model scores from smoke testing become headline results.

What this cannot establish

Two questions per MMLU subject cannot support reliable subject rankings. A one- or two-point gain may be inconclusive. Wikipedia may hurt HellaSwag. Public benchmarks may have appeared in training.

AWS timing does not establish laptop or Raspberry Pi performance. Native weight bytes are verified; actual runtime memory and quality are still unknown.

$200 is the ceiling, not the target.

Controls to implement before launch

  • One worker maximum; an initial two-hour instance lease, renewed only within the remaining envelope.
  • Reserve estimated batch liability before dispatch; stop scheduling at 80% of the stage allocation until remaining charges are reconciled.
  • Separate scheduled termination watchdog plus process timeouts; persist results before normal teardown.
  • Delete temporary disks and IPs; inventory retained S3 artifacts and their continuing cost.

What is already implemented?

A local planner, deterministic panel selection, historical inventory, provider-independent retrieval logic, a local likelihood adapter and a separate report starter. Twelve offline tests passed at the blueprint’s creation.

Still pending: current-model compatibility, full dependency locks, real retrieval providers, AWS infrastructure, runtime spending controls, actual measurements and offline score replay. AWS billing alerts alone are delayed and are not hard spending caps.

06 / Approval checkpoint

Review the plan before it runs.

The proposed decision is: three base checkpoints under 5 GB each, native BF16, three retrieval arms, a temporary AWS worker in us-west-2, and a $20 smoke test inside a $200 total ceiling.

  1. Model choice: Qwen3.5 0.8B Base, Qwen3.5 2B Base, Llama 3.2 1B base. Keep the original 3B results as historical context.
  2. Architecture: EC2 batch inference + local retrieval, S3 artifacts, SSM/IAM/CloudWatch and expiry controls. Existing Netlify publication stays in place.
  3. Execution gate: review the compatibility findings and dated cost estimate; then explicitly authorize the smoke test. No paid execution follows automatically from publishing this page.
